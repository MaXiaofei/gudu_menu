# 食集统一评价设计方案（menu review）

> **状态**：方案稿 v0.1（待用户确认原型后实施）
> **日期**：2026-08-08
> **范围**：menu-flutter（APP）+ menu-api（后端）
> **关联**：`docs/pantry-shopping-redesign.md`（完成结果页为做菜闭环一部分）、原型批次 44829

---

## 1. 背景

做菜完成结果页（cooking-deduct-modal 原型）现在把食集里**每道菜都列出来、各带一个「评价」按钮**——列得长、入口碎。用户要求：结果页只保留**一个统一评价入口**，点击跳转到统一评价页，在那里可以**对食集整体**和**食集里每一道菜**分别做评价。

现状：评价系统是**单菜维度**（`review` 表 dish_id 必填 + 星级 + 口味/难度/营养均衡/外观四维度 + 文字 + 图片）；**没有食集级评价**。食集完成态「去评价」是弹窗选一道菜再进单菜页。

## 2. 已确认决策

1. **食集整体评价复用单菜四维度**（口味/难度/营养均衡/外观，dict group=review_dimension）+ 星级 + 文字 + 图片，与单菜评价体验一致；
2. **单菜评价不关联食集**：从统一页进入单菜评价，提交时只带 dishId（纯菜品维度），不存 menuId。

## 3. 交互设计

### 3.0 入口全景（评价中心闭环）

| 入口 | 位置 | 时机 | 状态 |
|---|---|---|---|
| 做菜完成结果页「去评价 ›」 | 完成结果页 | 立刻评 | 新设计（§3.1） |
| 食集完成态底部「去评价」 | 食集详情 | 事后从食集进 | 改跳统一页 |
| 食记单条·逐道补评 | 食记详情 | 事后补评 | 原型已设计，Flutter 待做 |
| 菜谱详情「点评」 | 菜谱详情 | 单菜评 | 已有（保留） |
| **「我的」tab → 我的评价** | 我的 tab | 主动回顾/补评 | **新增（§3.4）** |

### 3.4 我的评价（评价中心，新增）

- 入口：我的 tab 功能项卡加「我的评价」（⭐ 图标）；
- 页面 `/my-reviews`：
  - **待评价**：已完成但没评完的食集（食集整体未评或还有菜未评）→ 点进统一评价页；
  - **我评过的**：食集评价 + 菜品评价历史（名称/星级/时间）→ 点进可修改；
- 后端：`GET /review/mine` 一个聚合接口（评价历史 + 待评价食集）。

### 3.5 菜谱详情均分（增强）

- 菜谱详情页在「点评」按钮旁/食材头显示该菜均分（`GET /review/dish/{dishId}/avg` 已有）；
- 后端 dish 详情接口直接带 avg 字段（免前端二次请求）。

### 3.1 完成结果页（入口改造，替代"每道菜一个评价按钮"）

```
这顿饭的菜 · 吃完别忘了评价
┌────────────────────────────────────┐
│ 番茄炒蛋 · 清蒸鲈鱼 · 蒜蓉菠菜      │
│                          [去评价 ›] │
└────────────────────────────────────┘
```

一行菜名（点菜名仍可进单菜页？——不，菜名纯展示）+ 一个「去评价 ›」按钮 → 跳 `/menu/{id}/review`。
底部「查看食记」/「‹ 返回食集」不变。

### 3.2 统一评价页（新页面 `/menu/{id}/review`）

```
‹ 评价这顿饭
今晚的饭 · 7/2 · 3 道菜

食集整体评价
┌────────────────────────────────────┐
│ 这顿饭整体怎么样？         [评价 →] │
│ （已评后：口味 ★★★★☆ 难度 ★★★☆☆ │
│   营养均衡 ★★★★☆ 外观 ★★★★☆ ✓）│
└────────────────────────────────────┘

这顿饭的菜
┌────────────────────────────────────┐
│ [图] 番茄炒蛋    已评 ★★★★☆  [评价] │
│ [图] 清蒸鲈鱼    未评          [评价] │
│ [图] 蒜蓉菠菜    未评          [评价] │
└────────────────────────────────────┘
```

- **食集整体评价卡片**：未评时显示「评价 →」；已评后显示四维度均分 + ✓ 已评，可再次点入修改；
- **菜品列表**：每道菜（封面/名称）+ 已评星级或「未评」+ 「评价」按钮 → 单菜点评页 `/dish/:id/review`（现有页，评完返回统一页刷新状态）；
- 菜品行已评状态 = 该菜最近一条 review（`GET /review/dish/{dishId}/avg` 已有，统一页 overview 接口批量带回）。

### 3.3 食集整体评价表单（点「评价 →」进入，复用单菜点评组件）

```
‹ 评价这顿饭
今晚的饭 · 7/2 · 3 道菜

这顿饭整体怎么样？
★ ★ ★ ★ ★（5 星，默认 5）

口味       ★★★★☆
难度       ★★★☆☆
营养均衡   ★★★★☆
外观       ★★★★☆

写点评价（选填）
[________________________]
[添加图片]

              [提交评价]
```

- 提交时 `menuId` 而非 `dishId`；其余字段与单菜评价完全一致；
- 提交成功返回统一页，食集卡片显示已评状态。

## 4. 数据模型（V43）

```sql
-- review 表：dish_id 改可空 + 加 menu_id（食集评价；与 dish_id 二选一）
ALTER TABLE review MODIFY dish_id BIGINT NULL;
ALTER TABLE review ADD COLUMN menu_id BIGINT NULL;
CREATE INDEX idx_review_menu ON review(menu_id);
```

- `review_score` 不变（食集评价同样用四维度子表）；
- 校验：提交时 `dishId`/`menuId` 至少一个（service 层）。

## 5. 接口设计

| 接口 | 方法 | 说明 |
|---|---|---|
| `POST /review` | 改 | `ReviewSaveDTO` 加 `menuId`（可选）；`dishId` 改可选；service 校验二选一 |
| `GET /review/dish/{dishId}/avg` | 保留 | 单菜均分（菜品行已评状态用） |
| `GET /review/menu-overview/{menuId}` | **新增** | 统一页数据：食集信息（名称/时间/菜品数）+ 食集已评状态（最近一条 review 星级/维度均分）+ 每道菜（dishId/名称/封面/已评星级或 null） |
| `GET /review/menu/{menuId}` | 新增 | 食集评价列表（详情页/未来扩展） |
| `GET /review/mine` | **新增** | 我的评价：① 评价历史（食集+菜品，名称/星级/时间）② 待评价食集（DONE 且未评完） |
| dish 详情接口 | 改 | 带 `avgRating`（该菜均分，菜谱详情显示） |

## 7. 实施顺序

1. **后端**：V43 迁移 + Review 实体/DTO/Service/Controller 改造（menuId 支持 + overview 接口）+ 单测；
2. **Flutter**：抽 ReviewForm 公共组件 → 食集评价表单页 → 统一评价页 → 路由与入口改造；
3. **做菜结果页入口**（随 P3 做菜闭环）：结果页"这顿饭的菜"区块改为统一入口。

## 8. 不做（范围外）

- 食集评价不做图片以外的富媒体（视频等）；
- 菜品行不做"去评价"之外的操作（如查看历史评价列表）；
- 评价与库存/采购无联动。
